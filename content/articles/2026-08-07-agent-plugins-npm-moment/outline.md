# 文章大纲：Agent 的“npm 时刻”来了，但真正的坑才刚开始

## 推荐标题

《Agent 的“npm 时刻”来了，但真正的坑才刚开始》

备选标题：

1. 《Agent Plugin 终于有统一包装了，离真正的 npm 还差五层》
2. 《Skills 和 MCP 被装进同一个盒子后，安全问题才刚开始》

推荐保留 Issue 原标题。它有足够张力，但正文开头会明确：“npm 时刻”指包格式开始统一，不代表 registry、lockfile、签名、权限和沙箱已经成熟。

## 一句话核心判断

Agent Plugins 1.0.0 让 Agent 能力第一次拥有跨客户端的公共交付单元；它降低了复用成本，也降低了恶意指令和越权工具的传播成本。对程序员来说，下一步不是多装插件，而是把插件当软件依赖管理。

## 目标读者与写作目标

- 读者：正在使用 Claude Code、Codex、Cursor、GitHub Copilot、Kiro 等 Coding Agent 的程序员、架构师与平台团队；
- 目标：读者看完能分清 Skills、MCP、Agent Plugins 三层职责，知道 1.0.0 的真实边界，并能为团队建立第一版插件准入规则；
- 建议长度：2400～2800 字；
- 文章类型：技术观点文，不写成发布公告翻译或安装教程。

## 文章结构

### 开头｜你安装的到底是一段说明，还是一段权限？（约 250 字）

从程序员熟悉的场景切入：为了让不同 Coding Agent 使用同一套代码审查/部署能力，团队要分别复制 Skill、MCP 配置和客户端 manifest，几份包装很快漂移。

接入新闻事实：Google 8 月 6 日宣布加入 Agent Plugins 核心维护团队；原始参与者来自 Amazon、Cursor、Microsoft、OpenAI、Vercel。

尽早给出判断：

> 这次真正统一的是“包装盒”。说它是 Agent 的 npm 时刻没有错，但这个 npm 现在只有包格式，还没有完整包管理与信任体系。

事实依据：S01、S02。

### 第一部分｜有了 Skills 和 MCP，为什么还缺一个 Plugin？（约 430 字）

先用工作现场解释三层关系：

- Skills 负责“怎样做”：流程、说明、脚本和参考资料；
- MCP 负责“怎样接”：连接外部工具、数据与服务；
- Agent Plugins 负责“怎样一起交付”：让相互配合的 Skill 与 MCP Server 用同一目录跨客户端移动。

点出旧问题：组件本身可以复用，外层 manifest、目录、MCP 配置形状和 transport 推断却各不相同。为第二个客户端再做一份包装，版本迟早漂移。

保留一个最小目录示例，不逐项翻译规范：

```text
my-plugin/
├── plugin.json
├── skills/
├── mcp.json
└── com.example.client/
```

落点：标准化不是为了让所有客户端变得一样，而是把公共核心和厂商扩展分开。

事实依据：S01、S02、S08。

### 第二部分｜1.0.0 标准化了什么，又故意没管什么？（约 520 字）

讲清四个已标准化点：

1. 根目录必须有 `plugin.json`；
2. Skills 固定放在 `skills/`，MCP 配置固定放在 `mcp.json`；
3. v1 的公共组件只有 Skills 与 MCP Servers；hooks、agents、commands 等走客户端扩展；
4. 独立组件独立失败，某个 MCP Server 启动失败不应拖垮整个插件。

随后写三个容易误解的边界：

- compatible 不等于 feature parity：客户端可以只支持一种组件或部分 transport；
- 包路径不能逃逸不等于 MCP 子进程被沙箱隔离；
- `version` 建议使用 SemVer，但插件依赖、lockfile、更新协议都没有定义。

用一句话收束：

> v1 的克制是优点。它先让公共部分有地方落脚，但也把大量风险明确留给了客户端和使用团队。

事实依据：S02、S03、S04、S05。

### 第三部分｜为什么“能安装”绝不能等同于“能信任”？（约 580 字）

这是全文的核心冲突，拆成三层攻击面：

#### 1. 指令层

`SKILL.md` 会进入模型上下文。恶意内容不一定长得像漏洞代码，也可能伪装成“工作步骤”，诱导 Agent 读取文件、泄露凭据或绕过约束。

#### 2. 代码与进程层

Skill 可以携带脚本，`mcp.json` 也可以声明本地进程。MCP 官方安全文档明确提醒：本地 Server 若无沙箱，可能以客户端权限执行命令。

#### 3. 工具与服务层

远程 MCP 的工具描述、返回数据和授权边界都可能被滥用。研究已把 tool poisoning 列为值得关注的客户端攻击面，但论文只作为风险信号，不夸大为普遍结论。

给出本文判断：

> 包格式消除了分发摩擦，也会把单点坏能力变成跨客户端供应链问题。这个风险比普通依赖多一层：插件既能带代码，也能改变 Agent 怎样理解任务。

事实依据：S08、S09、S10、S11、S12、S13。

### 第四部分｜真正的“npm 时刻”，还要补齐哪几层？（约 520 字）

不列抽象名词，改用五个团队问题推进：

1. **从哪里来**：发布者身份、源仓库、签名与 provenance；
2. **里面有什么**：脚本、二进制、MCP Server、依赖与 SBOM；
3. **装的是哪一版**：版本、commit/digest、锁文件、升级 diff 与回滚；
4. **运行时能做什么**：文件、网络、凭据和子进程的最小权限与沙箱；
5. **发生过什么**：安装、更新、授权、调用和失败的审计记录。

补充现实信号：Microsoft APM 等相邻项目已在尝试 lockfile、内容哈希、SBOM 和策略；Vercel Skills CLI 已在解决跨客户端安装。明确说明这些不是 Agent Plugins v1 的组成部分，只说明下一层竞争已经开始。

判断落点：未来的差异化不只是谁的插件最多，而是谁能让插件可验证、可限制、可回滚、可追责。

事实依据：S05、S15、S16、S17、S18、S19。

### 第五部分｜程序员现在可以先做三件事（约 470 字）

#### 1. 把 portable core 拆干净

将跨客户端通用的工作方法放在 `skills/`，把 MCP 配置收敛到标准 `mcp.json`；hooks、commands、agents 等厂商专属能力留在 extension namespace。不要为了“插件化”把单个简单 Skill 过度包装。

#### 2. 把插件纳入依赖审查

团队仓库固定来源与 commit/digest；升级时同时 diff `plugin.json`、`SKILL.md`、scripts 和 `mcp.json`；对脚本依赖生成清单，禁止明文秘密进入包；在 CI 中做 schema、静态扫描与回归任务。

说明边界：当前核心规范没有官方 lockfile，团队需使用客户端/相邻工具或自建清单实现。

#### 3. 默认隔离运行权限

新插件先在测试仓库和低权限环境运行；本地 MCP 启动前展示完整命令并人工批准；按插件限制文件、网络和凭据；高风险动作保留人工确认与审计。

说明边界：安全不能只写进 Skill 提示词，必须由客户端和运行环境强制执行。

事实依据：S02、S05、S10、S12。

### 结尾｜别再把 Plugin 当 Prompt 收藏夹（约 180 字）

不重复全文，只收束判断：

- Agent Plugins 最重要的变化不是多了一个 `plugin.json`，而是 Agent 能力开始成为可版本化、可迁移的工程资产；
- 从这一刻起，团队也应承担依赖治理责任；
- 最后一句建议：先挑一个低风险内部工作流做兼容性实验，同时留下来源、版本、权限和回滚记录。

建议收尾句：

> 当 Agent 能力开始像包一样传播，它就应该像依赖一样被审查，而不是像 Prompt 一样被随手收藏。
