## 一句话核心判断

MCP `2026-07-28` 删除的是协议层 Session，不是应用状态；它让普通请求能落到任意实例，也迫使团队把业务句柄、幂等、授权、任务恢复和审计设计成显式的分布式系统能力。

## 文章结构

### 开头｜三个 Pod 后面，为什么一个 Tool Call 会突然找不到 Session？（约 280 字）

从远程 MCP Server 的具体故障场景切入：

```text
initialize → Pod A → 返回 Mcp-Session-Id
tools/call → Pod B → 400 Session Not Found
```

过去的常见补丁是粘性路由，或者把协议 Session 放进 Redis。单机 Demo 没问题，一进 Kubernetes、滚动发布和 Serverless，连接状态就开始和基础设施较劲。

接入事实：MCP `2026-07-28` 正式规范移除了 `initialize` / `initialized` 和 `Mcp-Session-Id`。Google 8 月 5 日从云基础设施角度解读了这次变化。

尽早给出主判断：

> 这次不是状态消失了，而是 MCP 不再替应用把状态藏在传输会话里。

事实依据：S01、S02、S04、S19。

### 第一部分｜MCP 到底删掉了什么？（约 470 字）

用一组旧、新请求说明变化，不展示过长 Payload。

旧版：

- 先 `initialize` 协商版本和能力；
- 服务端可签发 `Mcp-Session-Id`；
- 后续请求携带 Session ID，通常回到保存状态的实例。

新版：

- 每个请求在 `_meta` 中携带协议版本与客户端能力；
- 客户端如需预先了解服务端，可调用 `server/discover`，但它不是强制的新握手；
- 普通请求不再和某个实例的协议 Session 绑定。

补充正式状态纠偏：`2026-07-28` 已于 7 月 28 日正式发布；Google 文章仍使用 RC/Beta 口径，正文以正式规范为准。

事实依据：S01、S02、S03、S04、S06。

### 第二部分｜为什么说它终于开始像普通云服务？（约 520 字）

从四个基础设施变化展开：

1. **负载均衡**：普通请求可以由任意实例处理，不再只为协议 Session 配 sticky routing；
2. **扩缩与发布**：Pod 重启、扩容和滚动发布不再需要保住某个协议 Session；
3. **网关治理**：`Mcp-Method`、`Mcp-Name` 与协议版本进入 HTTP 头，路由、计量、限流和审计无需先解析完整 JSON-RPC Body；
4. **缓存与 Serverless**：列表/资源结果有 `ttlMs`、`cacheScope`，无状态工具更适合 scale-to-zero。

使用 GitHub MCP Server 作为真实案例：它删除了 Redis Session 的初始化写入和每次请求读取，也不再为日志与 secret scanning 深度解析 Payload。

立即限定案例边界：GitHub 删除的是“只为协议 Session 存在的 Redis”。浏览器状态、审批、任务、锁和业务缓存仍可能需要 Redis 或数据库。

事实依据：S02、S04、S05、S09、S14。

### 第三部分｜状态没有消失，它只是换了五个位置（约 700 字）

这是全文核心。用一张分层图解释状态归属：

#### 1. 协议信息回到每个请求

版本、客户端能力与可选身份在 `_meta`；OAuth token 随每个 HTTP 请求发送并验证。

#### 2. 业务状态变成显式 handle

购物篮、浏览器实例、工作区等由服务端签发 ID，后续作为工具参数带回。handle 必须校验用户归属和权限，不能把旧 Session ID 原样换名。

#### 3. 中途补充输入进入 `requestState`

MRTR 先返回 `input_required`，客户端收集答案后重试。`requestState` 经过不可信客户端，需验签/加密、设置 TTL、绑定用户；多 Pod 共享密钥与 audience。

#### 4. 长任务进入 Tasks

Tasks 是双方协商支持的扩展。服务端先持久化任务，再返回 `taskId`；客户端轮询、补充输入或取消。协议给了生命周期，没有替团队提供任务队列。

#### 5. 通知进入请求范围的流和 Subscription Bus

无状态不等于没有 SSE。请求内进度仍能流式返回，`subscriptions/listen` 仍是一条长时 POST 响应；跨实例通知需要共享 Pub/Sub。

事实依据：S02、S04、S06、S07、S08、S12、S21。

### 第四部分｜负载均衡变简单后，可靠性问题反而更显眼（约 580 字）

围绕三个最容易被忽略的工程责任展开。

#### 重试不等于幂等

新版移除了 SSE Event ID 重放。流断开后客户端用新的 JSON-RPC 请求 ID 重发。有副作用的 Tool 必须有应用级幂等键、去重记录和补偿；JSON-RPC `id` 不能承担这个职责。

可用例子：退款、创建云资源、发通知。只讲设计原则，不虚构压测结果。

#### 每请求鉴权不能省

过去在 `initialize` 做一次权限判断的实现需要重构。新请求可能落到任意实例，token audience、scope、工具权限和业务 handle 归属都要在请求边界验证。HTTP 方法头方便网关策略，但头部不是信任来源。

#### 可恢复必须被验证

普通请求跨 Pod、MRTR 跨 Pod、Task 在进程退出后恢复、通知跨副本送达，是四种不同问题。不能用“服务无状态”一句话代替故障演练。

事实依据：S04、S05、S07、S08、S12。

### 第五部分｜迁移前先做这五项检查（约 500 字）

不写成过长清单，收敛为五个动作：

#### 1. 看清版本分布

记录客户端/SDK 协议版本、现代协商成功率和 legacy 回退率。旧客户端仍可能要求 `initialize` 与 Session。

#### 2. 搜出所有隐式状态

查找 `Mcp-Session-Id`、内存 transport Map、initialize 缓存、连接级能力、GET/SSE 通知和 EventStore 假设。

#### 3. 给副作用工具补幂等

由业务定义 idempotency key、唯一约束、重复结果和补偿路径。

#### 4. 做跨实例故障注入

在两轮 MRTR 之间切 Pod，在 Task 运行中重启 Worker，重复同一业务请求，并验证跨用户 `requestState` 重放被拒绝。

#### 5. 分阶段下掉旧 Session 设施

先让新旧协议双栈，观察错误码、重试、重复执行和恢复失败，再决定移除 sticky routing 与 Session Store。

结论：正式规范可以进入迁移计划，但“SDK 支持”不是生产验收条件。

事实依据：S09、S10、S12、S13、S20。

### 结尾｜Agent 开发正在回到分布式系统常识（约 200 字）

不重复全文，回到程序员能力：

- Tool Schema 决定“能调用什么”；
- 状态机、幂等、授权和恢复决定“出故障后还能不能相信它”；
- MCP 这次把协议层的基础设施障碍拿掉了，也让应用层责任更难被隐藏。

建议收尾方向：

> 下一次把 MCP Server 扩到三个副本时，不要只看请求能不能被负载均衡。主动让一台实例在请求中途退出，再看系统会不会重复执行、串错用户，或者丢掉一项长任务。那才是无状态架构真正的验收题。
