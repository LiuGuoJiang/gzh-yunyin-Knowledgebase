## 二、结论先行

本题最有价值的判断不是“以后都要用 stacked PR”，也不是“再部署一个 AI Review Agent”，而是：

> AI 压低的是代码生成成本，没有自动增加人的理解、验证和责任带宽。AI 原生研发流程的基本交付单元，应从“一次生成了多少代码”改成“一次交付了多少可理解、可验证、可回滚的变更”。

GitHub Stacked PR 与 OpenCodeReview 分别处理这条链路的两个不同问题：

1. Stacked PR 处理变更结构：把一个大任务表达成有依赖顺序的小变更图。
2. OpenCodeReview 处理评审执行：把文件选择、规则匹配、覆盖记录、评论定位等可确定环节交给程序，把需要语义理解的环节交给 LLM。

二者都不是“让 Agent 自由发挥”的证明，反而说明 Agent 越强，越需要把自由度装进明确的工程边界。

## 三、关键事实核验

### 1. GitHub 确实在连续强调 stacked sessions / stacked PR

- 2026-07-30，GitHub Blog 发布 Cassidy Williams 的个人案例：她用 GitHub Copilot app 改造一个旧项目，第一次试图一次性完成失败；随后把样式迁移与移除 `react-bootstrap` 拆成前后依赖的 session 和 PR。
- 文中对 stack 的定义是：同一仓库中的一系列 PR，每个 PR 以它下面一层 PR 的分支为目标，最终形成指向主分支的有序链。
- 2026-08-04，GitHub Blog 又用“购物助手增加商品搜索”的示例演示如何把一个 1,721 行左右的 AI 生成 PR 拆成四层：数据目录、搜索 API、聊天接入、引用卡片 UI。
- 这 1,721 行是 GitHub 教程中的示例，不是行业平均值，也不是对所有 AI PR 的统计结论。正文应明确其性质。

### 2. GitHub Stacked PR 目前是 public preview

阶段一初次核验时，旧版 `gh-stack` 文档仍标注 Private Preview。阶段二事实复核时，官方入口已跳转到新版 GitHub Docs，新文档明确标注 Public Preview，并说明功能仍可能变化。正文应以最新状态为准，不能继续写成私有预览，也不能写成已经 GA。

官方能力包括：

- PR 页面展示 stack map，每层只显示相对下一层分支的 diff。
- 分支保护规则针对整条 stack 的最终目标分支评估。
- 每一层 PR 都运行 CI，按最终 stack base 评估。
- 可以从底向上一次合并整条或连续的一部分 stack。
- `gh stack` CLI 支持创建层、级联 rebase、push、submit、sync；Agent skill 可把工作流说明提供给 Coding Agent。

已核验的限制与成本：

- 功能处于公开预览，仍可能变化。
- 修改底层 PR 后，上层分支需要级联 rebase；GitHub 可以执行服务端级联 rebase，`gh stack` 也支持本地处理，但冲突和分支同步成本没有消失。
- 所有分支必须在同一仓库，暂不支持跨 fork stack。
- 当前不支持 GitHub Desktop；官方同时提供 GitHub CLI、网页、Mobile、Webhook、REST API 和 GraphQL 支持。

因此 stacked PR 解决的是“依赖链可见、每层 diff 可审查、整链状态可管理”，没有消除依赖和冲突本身。

### 3. “小 PR”不能简化成机械行数指标

Google 的代码评审工程实践给出的更准确标准是“一次自包含的变更”：

- 只解决一件事；
- 带上相关测试；
- 审查所需上下文在该变更、描述、代码库或已审过的前序变更中可获得；
- 每次合入后系统仍保持可工作；
- 100 行通常合理、1000 行通常过大，但没有统一硬阈值，文件分布与概念复杂度同样重要。

这为文章提供了一个重要纠偏：目标不是把一个巨型 PR 生硬切成十个无法独立验证的碎片，而是把它拆成有清晰职责、验收条件和回滚边界的变更层。

### 4. OpenCodeReview 的核心价值是“把确定性环节写成程序”

截至 2026-08-05：

- GitHub 仓库主分支核验 commit：`533b526b4ca671712191997adb3f2fac7dd93f13`。
- 最新 release：`v1.8.8`，发布于 2026-08-04。
- Apache-2.0 许可证；GitHub API 查询约 19,030 Stars。Star 数是动态快照，只能用于说明关注度，正文没有必要突出。

README 与架构文档显示，开源版主要流程为：

```text
Git diff / 工作区 / commit / range
        ↓
文件过滤与路径规则解析
        ↓
按文件运行 review 子任务（受并发限制）
        ↓
LLM 通过 file_read / code_search / file_read_diff 等工具补上下文
        ↓
评论定位、过滤与结构化输出
        ↓
CLI / JSON / CI 回贴 PR
```

确定性工程承担：

- 从 Git 解析审查输入与 diff 范围；
- 二进制、目录、扩展名、include/exclude 等文件过滤；
- 按路径解析项目/个人/内置规则；
- 覆盖清单、运行 manifest 与会话状态；
- 根据 diff hunk 或文件内容解析评论行号；
- JSON 输出与 CI 回贴流程。

LLM Agent 承担：

- 理解单个文件当前变更；
- 根据需要读取完整文件、其他 diff 或搜索仓库；
- 针对较大 diff 先形成评审计划；
- 做业务语义、跨上下文和非固定规则的判断；
- 生成结构化问题与修复建议。

一个需要准确表达的细节：当前公开架构文档写的是“每个文件独立会话”，跨文件信息通过工具按需读取，并不是所有文件共享一个巨大上下文。README 的产品概述使用了“smart file bundling”的表述，但当前源码与详细架构文档更明确地描述 per-file subtasks。正文应使用后者，避免放大营销描述。

### 5. “确定性”不等于默认配置天然正确

OpenCodeReview 文档也暴露了几个工程边界：

- 默认文件过滤会排除多种常见测试文件模式，项目可以通过 `include` 显式纳入。这意味着团队必须审查默认策略，不能把工具装上就视为覆盖完整。
- 架构文档明确写出：每个文件独立评审，跨文件只通过工具获取上下文；这让成本和执行更稳定，但跨文件推理能力仍受模型调用与工具使用影响。
- 仓库当前开放 Issue 包括重复评论、稳定 finding fingerprint、大文件策略、模型兼容和更丰富需求上下文等问题，说明项目仍在快速演进。
- README 中的 benchmark、内部使用规模和效果数据均为项目方自报。若正文引用，必须标注“官方自报”，不能当作独立验证。本篇不需要依赖这些营销数字来成立。

正确的文章判断应是：OpenCodeReview 提供了值得借鉴的架构分工，不等于它已经证明 AI Review 可以替代人工审核。

### 6. 现有研究支持“AI Review 应增强人，而不是替代人”

2026 年 MSR 论文对 AIDev 数据集中 3,109 个带评论评审状态的 AI 相关 PR 进行分析：

- 在论文选定的 commented 子集中，纯代码评审 Agent 的 PR 合并率为 45.20%，纯人工评审为 68.37%。
- 98 个关闭的纯 Agent 评审 PR 中，60.2% 落入论文定义的 0～30% 信号比例区间。
- 作者结论是代码评审 Agent 应增强而非替代人。

但必须同时保留研究边界：

- 数据来自 GitHub 开源项目与 AIDev 数据集，不能直接推广到企业私有仓库。
- 合并率差异是相关性，不能证明“因为 AI Review 所以没合并”。
- signal/noise 使用关键词与人工校验构造，仍存在分类偏差。

这组研究适合支持“人工责任门仍有必要”，不适合用来证明所有 AI 评审工具效果差。

## 四、国内开发者平台观察

### 稀土掘金

近期中文文章的关注点主要集中在两类：

1. OpenCodeReview 相比“让通用 Agent 看一眼代码”的区别，是 diff 范围、规则、输出和 CI 集成可配置、可复用。
2. Agent 一次修改多个关注点后，Git 历史与 PR 需要回到语义变更单元；stacked PR 被视为让依赖显式化的一种方式。相关文章发布时记录的 private preview 状态已过时，产品状态以 GitHub 当前 public preview 文档为准。

这些观点与官方资料基本一致，可用于理解国内开发者关心的落地点，但不承担关键事实证明。

### 知乎

OpenCodeReview 相关高信息量文章主要来自阿里/千问云认证账号，重点讨论：

- 通用 Agent 可能出现覆盖不全、定位漂移、提示词波动；
- 评审规则越多不一定越好，需要按路径、模块和业务信号收敛作用域；
- 需求背景不足时，AI 很难判断实现是否满足业务约束。

这是厂商实践观点，不是独立第三方结论。文章可吸收“规则必须限定作用域”和“PR 描述要包含验收语义”这两个工程启发，不直接照搬其效果数字。

### CSDN

检索到的内容以项目介绍、转载和安装说明为主，暂未发现足以支持新技术结论的独立实践数据。本篇不采用 CSDN 内容作为事实依据。

### 争议与常见误解

- 误解一：小 PR 等于规定行数。更可靠的标准是单一关注点与独立验收。
- 误解二：stacked PR 让每层完全独立。它只是让依赖显式，底层变化仍会向上游传播。
- 误解三：再加一个 Review Agent 就能补齐人类评审带宽。研究和工程实现都表明，噪声、上下文、规则作用域与责任归属仍需人工治理。
- 误解四：CI 绿灯等于可合并。CI 只能验证写进测试和规则的部分，架构边界、业务意图和风险接受仍需负责人判断。
- 误解五：确定性流程会限制模型能力。更准确的说法是，让程序守住覆盖与定位，让模型集中处理语义，可以减少无谓自由度。

## 五、可形成的原创观点

### 主判断

AI Coding 的生产力单位，不应是“生成代码行数”，而应是“可验证的小变更”。

### 判断依据

1. 代码生成速度可以通过模型并行放大，但人的理解与责任不能同比扩容。
2. 大 diff 混合多个关注点，会让审查、定位、回滚和责任边界同时变差。
3. Stacked PR 把任务表达为依赖图，让审查者一次只承担一层认知负担。
4. OpenCodeReview 展示了一个更稳健的 AI 工程模式：确定性流程控制范围与输出，LLM 处理语义判断。
5. AI 评审存在噪声和上下文边界，最终责任不能外包给另一个模型。

### “Agent 时代 PR 四原则”

1. 单一关注点：一层只解决一个可描述、可验收的问题。
2. 依赖显式：前后置关系写进 stack、PR 描述和接口契约。
3. 逐层验证：每层包含相关测试并运行 CI，不把验证拖到最后一层。
4. 责任不外包：AI 做预审和语义扫描，人按风险等级做最终批准。

### 进一步的能力迁移

程序员的高价值工作将更多落在：

- 把模糊需求拆成有依赖关系的变更图；
- 为每层定义输入、输出、验收和回滚边界；
- 把稳定约束写进测试、lint、静态分析、策略与 CI；
- 为 LLM 提供必要的业务背景，并识别它无法负责的判断；
- 对最终上线结果承担责任。

这不是从“写代码”迁移到“只写 Prompt”，而是从代码生产者进一步转向边界设计者与验收负责人。

## 六、建议落地清单

### 个人或小团队

- Agent 任务默认只允许一个 concern；发现顺手重构时新开层，不混入当前 PR。
- PR 描述回答四件事：为什么改、这一层改什么、不改什么、怎么验证。
- 可以试用公开预览中的 `gh stack`，也可以先用普通 Git 分支实践同样的拆分原则，不把工具可用性当作流程改造的前提。
- 每层提交前至少运行受影响测试、lint、类型检查；高风险层补人工验证。
- AI Review 先用于高重复、可规则化检查，把建议作为线索，不自动全部采纳。

### 团队

- 建立变更风险分级：文档/低风险配置、普通业务、高风险安全/数据/权限。
- 低风险允许“确定性检查 + AI 预审 + 人工抽查”；中风险要求人工批准；高风险要求领域 owner 与安全/数据责任人。
- 记录每层的负责人、依赖、CI、回滚方式与上线观察项。
- 衡量 review wait time、返工轮数、回滚成功时间、缺陷逃逸率，而不是 AI 生成行数。
- 定期抽检 AI 评论的准确性与采纳结果，删除高噪声规则。
