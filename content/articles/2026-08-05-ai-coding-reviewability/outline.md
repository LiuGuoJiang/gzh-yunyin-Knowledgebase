## 二、核心命题

AI 把编码阶段的边际成本快速压低，却没有同步扩大人类的理解、验证和责任带宽。巨型 AI PR 会把节省下来的编码时间重新消耗在排队、补上下文、返工与高风险合并上。

真正的解决办法不是简单地再加一个自由发挥的 Review Agent，而是重构变更交付链路：

- 用 stacked PR 把大任务表达成有依赖顺序的变更图；
- 用确定性程序守住范围、规则、覆盖、定位和 CI；
- 用 LLM 处理需要上下文的语义判断；
- 用风险分级与人工责任门完成最终验收。

文章最终落点：AI 原生团队衡量的不是生成代码量，而是单位时间交付了多少可理解、可验证、可回滚的变更。

## 四、正文结构

### 开头｜写代码变快后，排队的为什么还是人（约 300 字）

切入事实：GitHub 8 月 4 日的教程中，一个商品搜索功能一次生成约 1,721 行变更，混合了数据、API、前端接入与 UI 状态。代码几分钟可以产出，reviewer 面对的仍是一整块需要重新建立上下文的 diff。

关键转折：

> AI 缩短的是“从需求到代码”的时间，不是“从代码到可信变更”的时间。

明确不制造焦虑：问题不在 AI 写得快，而在团队仍用人工时代的 PR 结构接收 Agent 产能。

### 第一部分｜新瓶颈不是产码，而是理解带宽（约 400 字）

解释巨型 AI PR 的三重成本：

1. 多个 concern 混在一起，reviewer 无法快速建立正确心智模型；
2. 问题定位与返工互相牵连，改一处需要重新看整块 diff；
3. 合并与回滚粒度过大，CI 绿灯也无法覆盖未写入测试的业务意图。

引用 Google 工程实践做纠偏：小变更的本质是“一项自包含的改变”，不是死守行数。相关测试、上下文和系统可用性必须同层成立。

本节判断：AI 让“写一大坨”更便宜，也让错误的变更结构更容易发生。

### 第二部分｜GitHub 的解法：把 PR 从一个包裹变成依赖图（约 550 字）

串联 GitHub 两个官方信号：

- 7 月 30 日：Copilot app 的 stacked sessions 案例；one-shot 失败后，把旧项目改造拆成前后依赖的 session。
- 8 月 4 日：用 Stacked PR 把商品搜索拆成数据 → API → 业务接入 → UI 四层。

用简洁文本图解释：

```text
main
└─ PR1：数据与校验
   └─ PR2：搜索 API
      └─ PR3：聊天接入
         └─ PR4：UI 与异常状态
```

说明实际价值：

- 每层只有一个主要 concern；
- 不同 owner 审不同层；
- 每层显示自己的 diff，并运行 CI；
- 依赖显式，整条 stack 的状态可见。

同时写清限制：GitHub 当前处于 public preview，仍可能变化；底层变化会触发上层级联 rebase，冲突、分支同步和团队流程改造成本仍存在。团队也可以先用普通 Git 分支实践同样的拆分原则，不把特定工具当作前提。

本节判断：stacked PR 没有消灭复杂性，而是把复杂性从一个巨型 diff 还原成可见的依赖关系。

### 第三部分｜为什么“再加一个 Review Agent”还不够（约 600 字）

从 OpenCodeReview 切入，但不写成项目推荐软文。

先讲通用 Agent review 的风险：可能选错文件、漏看变更、规则作用域漂移、评论行号不准、输出噪声过高。问题不一定来自模型不够强，而是纯语言驱动缺少硬约束。

再拆 OpenCodeReview 的架构分工：

| 确定性程序 | LLM Agent |
|---|---|
| 解析 Git diff 与范围 | 理解变更语义 |
| 过滤文件、匹配路径规则 | 按需读取文件与搜索仓库 |
| 记录覆盖、解析评论位置 | 判断业务逻辑与上下文风险 |
| 结构化输出、接入 CI | 生成问题与修复建议 |

强调公开实现的边界：当前按文件独立运行 review，跨文件上下文通过工具读取；默认过滤与规则需要团队审查；项目仍有重复评论、大文件等开放问题。官方 benchmark 只作为厂商自报，不用于证明“已经优于人”。

引入 2026 年代码评审 Agent 论文作为警示：在其限定数据集中，纯 Agent review 的合并结果与评论信号均不支持“取消人工”这一结论；同时说明这只是相关性研究，不能外推为所有企业场景。

本节判断：AI Review 最适合成为预审层和语义扫描层，而不是责任转移层。

### 第四部分｜一套能落地的“Agent 时代 PR 四原则”（约 550 字）

#### 1. 单一关注点

Agent 任务一次只解决一个可描述、可验收的问题。顺手重构、依赖升级、格式化单开一层。

#### 2. 依赖显式

把前后置关系写进分支/stack、PR 描述和接口契约。PR 描述回答：为什么改、这一层改什么、不改什么、如何验证。

#### 3. 逐层验证

每层包含相关测试，独立跑 lint、类型检查、单测或必要的 E2E。底层失败时阻止上层合并；CI 不只在整条链最后跑一次。

#### 4. 责任不外包

确定性规则检查已知问题，LLM 查语义风险，人按风险等级批准：低风险可抽查，中风险必须人工批准，安全、权限、资金、数据迁移等高风险由领域 owner 把关。

给出一句可执行的团队规则：

> Agent 可以提交变更、运行检查和提出意见，但不能同时定义验收标准、证明自己通过、再批准自己上线。

### 结尾｜程序员的价值从写得快，迁移到边界设计与验收（约 300 字）

回到“这件事对程序员意味着什么”：

- 更重要的能力是把需求拆成变更依赖图；
- 把稳定约束沉淀为测试、规则和 CI；
- 知道哪些语义判断可以交给 LLM，哪些责任必须由人承担；
- 让每次交付都可理解、可验证、可回滚。

最终判断：未来程序员不只是代码生产者，更是边界设计者和验收负责人。团队也应少看“AI 写了多少行”，多看 review wait time、返工轮数、回滚时间和缺陷逃逸率。
