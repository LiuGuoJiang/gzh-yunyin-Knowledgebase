## 二、核心命题

Luna 降价 80% 让一个原本模糊的架构问题变得非常具体：同等 Token 量下，Luna 的标准费用只有 Sol 的 1/25。继续让一条 Agent 工作流里的规划、实现、测试、分类和总结都使用同一模型，成本浪费会越来越明显。

但“全部换 Luna”不是答案。低价模型如果带来更长循环、更多重试和人工返工，最后可能更贵。

文章主判断：

> Agent 的成本优化不是换一个便宜模型，而是把任务拆成不同智力等级，让每一步使用能够稳定通过验收的最低成本模型。

工程上需要四个组成部分：任务分类、质量门、失败升级、步骤级成本观测。优化指标也要从“每百万 Token 多少钱”换成“每个合格结果的总成本”。

## 四、三种写法比较

### 方案 A｜纯降价快讯

- 结构：新价格 → 模型对比 → 适用场景。
- 优点：短、快、适合追资讯。
- 缺点：和普通产品新闻差异小，难以回答“程序员现在该改什么”。

### 方案 B｜架构变化 + 行动建议（推荐）

- 结构：降价事实 → 为什么不能全切 Luna → 步骤级路由 → 成本指标 → 最小落地路径。
- 优点：保留 AI自由圈的轻量节奏，同时形成明确技术判断和可执行建议。
- 缺点：需要控制术语密度，不能写成 3000 字架构长文。

### 方案 C｜完整路由教程

- 结构：路由器代码、配置、评测集、观测指标和灰度方案。
- 优点：实操性强。
- 缺点：Issue 没有指定技术栈，也没有真实项目数据；容易虚构参数并偏离本号资讯定位。

建议采用方案 B，只给一张路由示意图和五步落地清单，不提供未经项目验证的代码。

## 五、正文结构

### 开头｜Luna 的价格，突然只剩 Sol 的 1/25（约 180 字）

直接给事实：

- 7 月 30 日，Luna 输入 / 输出降至 `$0.20 / $1.20`，降幅 80%；
- Terra 降至 `$2 / $12`，降幅 20%；
- Sol 标准价保持 `$5 / $30`；Fast mode 最高 2.5 倍速度、价格 2 倍。

用一句话转折：

> 这次真正值得关注的，不是“便宜模型更便宜了”，而是同一条 Agent 工作流终于有了足够大的价差，逼着团队认真做分层。

边界：所有价格按每百万输入 / 输出 Token；工具调用、长上下文、缓存写入和 Fast mode 另有计费条件。

### 第一部分｜为什么不能把默认模型直接换成 Luna（约 300 字）

从 Agent 与普通问答的区别切入：一次任务会经历规划、检索、工具调用、实现、验证和总结，多次模型请求共享上下文，失败还会触发重试。

同样一项任务，Luna 单次调用便宜，不代表最终结果便宜：

- 规划错误会让后续步骤一起走偏；
- 工具调用和上下文重复会在循环里放大；
- 低质量结果需要强模型重做或人工返工；
- 错误外部操作的代价可能远高于 Token。

本节判断：最低 Token 价不是最低任务成本。真正要优化的是“一个通过验收的结果花了多少钱”。

### 第二部分｜模型选择正在从“应用级”下沉到“步骤级”（约 420 字）

引用 OpenAI 官方编码示例：Sol 负责消除不确定性和定义计划，Luna 负责明确修改、写和跑测试、评估结果；同时提醒官方也说不同工作流需要不同平衡。

用一张简图解释推荐架构：

```text
任务分类
  ├─ 可预测、可自动验收 → Luna
  ├─ 日常综合判断       → Terra
  └─ 高不确定性 / 高风险 → Sol / Sol Fast
             ↓
          质量门
      通过 / 升级 / 转人工
```

强调不是按任务名称机械映射，而是看四个信号：不确定性、错误代价、时延要求、是否有可靠验收。

给出易懂例子：

- Luna：结构化抽取、固定格式转换、已明确修改、可用测试自动验收的批量步骤；
- Terra：日常 RAG 回答、常规业务分析、需要综合上下文但风险适中的任务；
- Sol：需求澄清、复杂规划、高风险代码审查、失败代价高的决策；
- Fast mode：用户在等待且延迟价值足够高的 Sol 请求，不用于后台批处理。

本节判断：路由不只是“接三个模型”，而是给每一步建立选择依据和升级路径。

### 第三部分｜一套能落地的成本账本（约 350 字）

不放未经验证的“节省 80%”案例，给出指标框架：

```text
每个合格结果的总成本
= 模型 Token + 工具 + 重试 + 基础设施 + 人工复核 + 失败代价
```

建议至少记录：

- 路由到哪个模型、使用哪个处理档位；
- 输入 / 输出 / 推理 Token，缓存写入与读取；
- 工具调用、循环步数、重试和升级次数；
- 自动验收通过率、人工改写率、P50 / P95 延迟。

穿插两个必要提醒：

1. GPT-5.6 缓存写入要收费，缓存不是“打开就省”；要比较写入量和后续命中。
2. OpenAI 披露的 20% 服务成本下降、15% Token 生成效率提升是其内部工程结果，不是普通团队可直接复制的收益。

### 第四部分｜程序员现在可以怎么做（约 300 字）

五步最小落地法：

1. 只选 3～5 个稳定任务类别，不先做万能智能路由器。
2. 为每类任务写清验收标准，用同一批真实样本比较三档模型。
3. 选择“能稳定过线的最低成本模型”，先在影子模式记录建议，不立即切全量。
4. 加上失败升级、循环上限和人工责任门，再小流量灰度。
5. 最后按在线、后台和离线任务分别选择 Fast、Standard、Batch / Flex，并优化缓存。

补一句架构判断：模型路由会越来越像数据库读写分离——重要的不是多一个连接串，而是流量分类、质量门、回退和观测已经成为基础设施。

### 结尾｜便宜模型释放的是架构空间（约 150 字）

回到选题：Luna 的 80% 降价确实让高频、后台、批量型 Agent 更有经济性，但真正的收益要靠工程系统兑现。

收束观点：

> 贵模型只处理贵的不确定性，便宜模型处理可验证的规模。谁能把这条边界画清楚，谁才真正拿到了这次降价的红利。

不重复全文，不上升到“颠覆行业”或“程序员将被替代”。
