## 二、结论先行

这次最值得写的不是“又一个模型降价”，而是 OpenAI 把一套 Agent 成本架构公开说透了：

> 高能力模型负责消除不确定性和定义计划，低价模型负责已经说清楚的执行与验证；每一步是否值得使用更多智能，要由真实任务评测决定。

因此，模型选择正在从“整个应用固定一个模型”，变成“同一条 Agent 轨迹内按步骤路由”。

这不等于所有团队都应机械采用“Sol 规划、Luna 执行”。更稳妥的工程表达是：先定义每个步骤的验收条件，再选择能够稳定过线的最低成本配置；失败、低置信度或高风险任务向上升级，外部写入和不可逆操作仍保留人工责任门。

## 三、关键事实核验

### 1. 时间线与价格变化

| 时间 | 事件 | 已核验事实 |
|---|---|---|
| 2026-07-09 | GPT-5.6 系列正式发布 | Sol、Terra、Luna 全面可用；初始 API 价分别为 `$5 / $30`、`$2.50 / $15`、`$1 / $6`（每百万输入 / 输出 Token） |
| 2026-07-29 | OpenAI 发布效率工程文章 | 披露模型、推理系统和 Agent harness 的效率优化；Sol 参与 Kernel、推测解码和生产配置优化 |
| 2026-07-30 | OpenAI 宣布降价和 Fast mode | Luna 降价 80%，Terra 降价 20%；Sol 标准价不变；Fast mode 替代 Priority Processing |
| 2026-08-06 | 本次复核 | 官方模型页已显示新价格；早期搜索摘要和部分中文文章仍显示旧价，不能据摘要引用 |

当前标准 API 价格：

| 模型 | 定位 | 输入 / 百万 Token | 缓存输入 / 百万 Token | 输出 / 百万 Token | 相对变化 |
|---|---|---:|---:|---:|---|
| GPT-5.6 Sol | 旗舰能力 | $5.00 | $0.50 | $30.00 | 标准价不变 |
| GPT-5.6 Terra | 能力与成本平衡 | $2.00 | $0.20 | $12.00 | 输入、输出均降 20% |
| GPT-5.6 Luna | 高吞吐、成本敏感 | $0.20 | $0.02 | $1.20 | 输入、输出均降 80% |

同等输入、输出 Token 下，Luna 的标准 Token 费用是 Terra 的 1/10、Sol 的 1/25。这个比例只能说明单次推理价格差，不能直接等同于任务总成本。

补充计费边界：

- 三个模型的上下文窗口均为 1,050,000 Token，最大输出均为 128,000 Token。
- 输入超过 272K Token 时，整个请求按 2 倍输入价、1.5 倍输出价计费，并非只对超出部分加价。
- GPT-5.6 的缓存写入按未缓存输入价的 1.25 倍计费；缓存读取使用缓存输入价。应同时记录 `cache_write_tokens` 与 `cached_tokens`，不能只看命中次数。
- 工具型能力可能另收工具调用费；文章中的 Token 价格不代表完整 Agent 账单。

### 2. Fast mode 是时延溢价，不是降本选项

- 2026 年 7 月 30 日，Priority Processing 更名为 Fast mode。
- GPT-5.6 Sol 的 Fast mode 最高可达到标准处理的 2.5 倍速度，官方公告说明价格为标准处理的 2 倍，智能水平不变。
- Fast mode 适合高价值、面向用户且延迟敏感的请求；批量、离线和后台任务不应因为“快”而默认使用它。
- 若流量爬升过快，Fast mode 请求可能降级到标准速度并按标准费率计费，响应里的 `service_tier` 可用于核验实际处理档位。

### 3. OpenAI 给出的不是固定模型表，而是结果导向的选择原则

OpenAI 公告先列出四个决定因素：结果风险、错误代价、紧急程度和规模；随后给出一个编码工作流示例：

```text
Sol：消除不确定性、定义计划
  ↓
Luna：实现已明确的修改、编写和运行测试、评估结果
```

官方同时强调“另一个工作流可能需要不同平衡”，并建议用评测判断额外智能在哪些步骤真正改善结果。这意味着“Sol 规划、Luna 执行”是示例，不是普适规则。

### 4. OpenAI 披露的 20% 与 15% 是内部工程结果

- OpenAI 表示，在人工主导流程中，GPT-5.6 Sol 参与改写和优化生产 Kernel，相关工作帮助端到端模型服务成本降低 20%。
- Sol 还设计并运行数百个推测模型实验、监控训练和处理异常，相关改进让 Token 生成效率提高 15% 以上。
- 这些数字来自 OpenAI 自己的生产系统，没有独立复现，不应写成所有 Agent 团队可以获得的普遍收益。
- 更有迁移价值的经验是：优化对象不只在模型，还包括请求路由、调度、缓存、上下文管理、工具输出和重复工作。

## 四、技术上真正改变了什么

### 从应用级模型选择，变成步骤级资源分配

旧做法通常是：

```text
一个应用 / 一个 Agent → 一个默认模型 → 所有步骤同价
```

更合理的分层路由是：

```text
任务进入
  ↓
任务分类：类型、复杂度、风险、时延、是否可自动验收
  ↓
选择模型与处理档位
  ├─ 低不确定性、可自动验收 → Luna
  ├─ 日常综合判断、适度不确定性 → Terra
  └─ 高不确定性、高错误代价 → Sol / Sol Fast
  ↓
验证结果
  ├─ 通过 → 继续下一步
  └─ 失败 / 低置信度 / 超出边界 → 升级模型或转人工
  ↓
记录轨迹、成本、质量和延迟，更新路由规则
```

关键变化有三点：

1. **路由单位变小。** 不再只在请求入口选一次模型，而是在规划、检索、实现、测试、分类、格式化、总结等步骤分别选择。
2. **便宜模型必须配验证。** 结构化输出、测试、规则或人工抽检提供质量门；没有验收信号，就无法判断是否应该升级。
3. **路由规则要从数据中校准。** 任务类别、风险和复杂度只是起点，最终阈值要用本业务的真实分布和评测结果校准。

### 学术与行业资料支持，但也暴露边界

- ICLR 2025 的 RouteLLM 研究展示了“强模型 / 弱模型”动态路由的成本—质量空间；论文在部分基准上实现超过 2 倍成本节省，但 MMLU、GSM8K 等分布外任务上，未增强路由器一度接近随机路由。结论是路由可行，但训练与线上任务分布必须匹配。
- LMSYS 的开源实现要求针对实际查询校准阈值，并明确指出用公共数据校准后，线上强模型调用比例可能不同。
- Anthropic 的工程文章也把 routing 作为标准工作流：当输入类别可准确识别时，把常见简单问题交给更小模型，把困难异常问题交给更强模型。
- 2026 年的 AgentRouter 工作论文把路由推进到 Agent 轨迹的“逐步骤选择”，报告了成本下降与质量保留结果。但它是新近工作坊论文，数字来自作者实验，不应用来证明生产系统必然节省同样比例。

## 五、成本不能只看 Token 单价

### 一个透明的示例账本

假设 1000 次 Agent 步骤，每次都固定使用 20K 输入、4K 输出，暂不计算缓存、长上下文、工具费、重试和人工：

| 全部使用 | 单步 Token 费 | 1000 步 Token 费 |
|---|---:|---:|
| Luna | $0.0088 | $8.80 |
| Terra | $0.088 | $88.00 |
| Sol | $0.22 | $220.00 |

若静态假设 80% 路由 Luna、15% 路由 Terra、5% 路由 Sol，在完全相同 Token 量下，Token 费约为 `$31.24`，相比全部使用 Sol 低约 85.8%。

这只是展示价格杠杆的算术模型，不是本文实测，也不是生产节省承诺。现实中模型的输出长度、循环次数和成功率并不相同；一次错误动作或多轮重试，可能远高于省下的 Token 费。

### 更可靠的指标：每个合格结果的总成本

```text
每个合格结果的总成本
=（模型 Token + 工具调用 + 基础设施 + 重试 + 人工复核 + 失败代价）
 ÷ 通过验收的结果数
```

至少要记录：

- 任务类型与实际路由模型；
- 输入、输出、推理、缓存读写 Token；
- 工具调用次数和工具费用；
- 重试次数、升级次数、循环步数；
- 首 Token 延迟、总延迟、P50 / P95；
- 自动验收通过率、人工改写率、失败和回滚代价。

如果只看“每百万 Token 多少钱”，就会漏掉 Agent 最昂贵的部分：重复上下文、失败循环、无效工具调用和人工返工。

## 七、争议与常见误解

### 误解一：Luna 降价 80%，默认模型就应该全部换成 Luna

错误代价高、输入模糊、跨域规划或需要复杂语义判断的任务，低价模型即使 Token 便宜，也可能因失败、重试和人工返工变贵。正确问题是“哪个最低成本配置可以稳定通过验收”。

### 误解二：照抄“Sol 规划、Luna 执行”就完成了路由

官方明确说不同工作流会有不同平衡。某些团队可能由 Terra 规划、Luna 格式化；某些高风险流程的执行和复核都需要 Sol。路由表要来自业务评测，而不是来自产品命名。

### 误解三：路由只需一个任务分类器

生产路由至少还需要质量门、失败升级、重试上限、人工转交、缓存策略、服务档位选择和可观测性。分类错了却没有升级路径，错误会沿 Agent 轨迹继续放大。

### 误解四：Fast mode 也是成本优化

Fast mode 用更高价格购买低延迟，解决的是时效，不是单次 Token 成本。真正的架构能力是让用户交互、后台任务和离线评测使用不同处理档位。

### 误解五：模型路由能替代权限和责任控制

无论使用哪一档模型，外部写入、发布、付款、删资源、移动凭证等高影响动作都应有独立的授权边界。更便宜或更强都不是放宽权限的理由。

## 八、对程序员和团队的实际影响

### 开发者要新增的能力

- 把一条 Agent 任务拆成可分别验收的步骤，而不是只写一条长 Prompt。
- 为每步定义复杂度、风险、时延和验收标准。
- 设计失败升级与人工接管，不让模型在低质量循环里无限重试。
- 建立步骤级 tracing 和成本归因，让一次账单能追到具体任务与具体失败。
- 用真实业务样本做模型评测，避免只看通用 benchmark 或厂商案例。

### 最小可行落地顺序

1. 先选 3～5 个稳定任务类别，不做“万能智能路由器”。
2. 固定验收规则，在同一批代表性任务上比较 Luna、Terra、Sol 的成功率、总 Token、工具调用、重试和延迟。
3. 为每类任务选择“能稳定过线的最低成本模型”，先以影子模式记录路由建议，不立刻切主链路。
4. 增加失败升级、循环上限和人工责任门，再小流量灰度。
5. 最后才优化缓存、Batch / Flex / Fast 等处理档位，避免把多个变量同时改动后无法归因。

## 九、可形成的原创观点

### 主判断

Agent 的成本优化不是换一个便宜模型，而是把任务拆成不同智力等级，并为每一级建立可验证的质量门。

### 判断依据

1. Agent 一次任务包含多次模型调用和工具循环，步骤之间的难度差异远大于普通单轮问答。
2. Luna 与 Sol 的同量 Token 价差达到 25 倍，使“所有步骤用同一模型”的浪费更容易被看见。
3. OpenAI 官方示例、RouteLLM 研究和 Anthropic 工程实践都指向任务分流，但同时要求评测、校准与清晰分类。
4. 低价模型可能通过更长循环、更高重试和人工返工把成本吃回来，因此优化单位必须从 Token 变成合格结果。

### 可用表达

> 过去我们给一个应用选模型，接下来要给 Agent 的每一步分配模型。

> 模型路由真正像“数据库读写分离”的地方，不是多接几个模型，而是先定义流量类型、质量门和失败回退。

## 十一、事实表述红线

- 不把 OpenAI 内部 20% 服务成本下降、15% Token 生成效率提升写成行业平均或用户可直接获得的收益。
- 不把厂商 benchmark 或合作方引语当成独立验证。
- 不写“Luna 可以替代 Sol”或“所有执行任务都应该用 Luna”。
- 不把静态算术示例写成真实生产节省结果。
- 不使用 7 月 30 日前的旧价格；阶段二写作前再次打开官方模型页复核。
- 不虚构江小北的使用体验、账单、团队规模或上线结果。
- 不把预测写成现状；“模型路由会成为基础能力”应明确为工程判断。
