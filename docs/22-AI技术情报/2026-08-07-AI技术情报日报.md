## Agent Plugins 1.0.0：Skills 和 MCP 开始有统一“包装盒”


### 发生了什么

Google 8 月 6 日宣布加入 Agent Plugins 核心维护团队；这份由 Amazon、Cursor、Microsoft、OpenAI、Vercel 等共同推进的 1.0.0 工作草案，用固定目录和 `plugin.json` 将 Agent Skills、MCP Server 及客户端扩展装进一个可移植包。


### 为什么重要

MCP 解决“Agent 怎么调用工具”，Skills 解决“Agent 应该怎样做事”，但两者过去缺少统一的交付单元。Agent Plugins 补的是打包层：同一份能力可以有公共核心，也可以保留少量客户端适配，不必为每个 IDE 或 Agent 平台重新拼装。

更值得注意的是它没解决什么。当前 v1 只定义包格式，不定义安装、分发、权限、沙箱和来源可信度。它是生态互操作的起点，还不是插件安全标准。


### 对程序员的影响

做 Agent 工具的团队可以开始把可移植部分拆成 `skills/` 与 `mcp.json`，把厂商差异压到客户端扩展目录，减少重复维护。与此同时，插件客户端仍要自己承担签名校验、权限提示、依赖审计和 MCP 进程隔离。下载一个插件包，不等于可以放心执行其中的命令。

现在适合做格式兼容性试验，不适合把工作草案当成稳定 ABI。仓库结构、版本锁定、回归测试和供应链清单，应该从第一版插件就留下。


### 江小北观点角度

Agent 生态开始出现软件生态的轮廓：“能力”终于有机会成为可安装、可迁移、可组合的软件包。

但包装统一之后，风险也会被放大：坏能力传播得更快，过期依赖影响得更广。下一阶段的竞争重心会落到注册中心、签名、SBOM、权限模型与沙箱。程序员应把 Agent Plugin 当依赖包管理，别再当成一段可以随手复制的 Prompt。

## MCP 拿掉传输层 Session，开始按云原生基础设施设计


### 发生了什么

Google 8 月 5 日解读 MCP 2026-07-28 版本：核心协议改为无状态、自包含请求，并加入可供网关识别的 HTTP 头、按请求能力协商，以及异步 Tasks 等扩展能力；Google 同时提供 Python、TypeScript、Go、C# 的 Beta SDK 用于试验。


### 为什么重要

旧式会话把请求绑在某台 Server 上，扩容常常需要粘性路由，或者额外维护 Redis 会话。无状态请求让负载均衡、Serverless、故障切换和网关治理更直接；网关也能基于协议版本、方法与名称做路由、限流和审计，不必先解析完整消息体。

表面看是字段和握手方式调整，本质上是 MCP 从“客户端连接协议”走向“可运营的云服务协议”。


### 对程序员的影响

部署 MCP Server 的团队可以减少传输层会话设施，但业务状态不会凭空消失。授权上下文、重试幂等、长任务进度、用户补充输入和恢复令牌，都需要显式放进请求、任务对象或业务存储。

迁移时应重点压测负载均衡切换、重复请求、任务恢复和授权边界。官方仍建议先在 staging 验证 Beta SDK，不要把协议更新直接等同于生产成熟。


### 江小北观点角度

这里的“无状态”，只是重新决定状态归谁管。MCP 把连接状态拿掉后，Agent 工程的核心会更像分布式系统：显式状态机、幂等键、可恢复任务和全链路审计，比维持一条长连接更重要。

这也意味着 Agent 开发者要补一课后端基本功。只会写 Tool Schema 的团队，很快会在重试、恢复和权限一致性上交学费。

## Kimi K3 进入 GitHub Copilot，但 rollout 同日因 Actions 事故暂停


### 发生了什么

GitHub 8 月 6 日宣布 Kimi K3 在 Copilot 中正式可用，由 Fireworks AI 托管；公告随后加注，rollout 因一项影响 GitHub Actions 的事故暂时暂停，恢复后才会继续开放。


### 为什么重要

这次接入释放了一个明确信号：开源权重模型正在进入主流编程助手的统一模型菜单。模型、托管商、IDE 与计费平台可以分层组合，开发者选择模型时不再只看一家厂商的封闭产品线。

同日暂停也提醒我们：一个模型能不能用于日常开发，取决于 benchmark、托管链路和平台稳定性等一整套条件。


### 对程序员的影响

rollout 恢复后，开发者可以在 VS Code、JetBrains、Copilot CLI、云端 Coding Agent 等入口试用 Kimi K3。Business 与 Enterprise 默认关闭，需要管理员开启并评估开源权重模型相关的安全、合规和数据治理要求。

团队选型时应拿自己的仓库任务测修改正确率、工具调用成功率、延迟和单任务成本。GitHub 公布的价格是每百万输入 Token 3 美元、输出 Token 15 美元、缓存输入 Token 0.30 美元，但“开源权重”通过 SaaS 使用，并不等于本地部署或数据不出平台。


### 江小北观点角度

AI Coding 的模型选型正在从“谁的分数最高”变成一份运行时合同：谁托管、怎么计费、故障时能否切换、代码经过哪里、管理员能管到什么程度。

普通程序员可以多一个模型选项；技术负责人需要建立模型路由和降级预案。真正成熟的多模型开发平台，应该允许事故发生时平滑切换，而不是让整个研发流程跟着某次 rollout 停摆。

## Optimum Intel 2.1.0 补上新模型在 Intel 端侧的落地链路


### 发生了什么

Hugging Face 8 月 6 日介绍 Optimum Intel 2.1.0。该版本新增 Gemma 3n、Gemma 4 Unified、Qwen3-Omni-MoE、Qwen3-VL-Embedding、SmolLM3 和 FLUX.2 的 OpenVINO 导出与推理支持，并给出经过验证的 OpenVINO 2026.3、OpenVINO GenAI 2026.3、NNCF 3.3 版本组合。


### 为什么重要

新模型发布不等于它已经能在普通硬件上稳定运行。模型架构需要转换器、算子、量化和运行时逐层适配。Optimum Intel 这类兼容层更新，决定了 Intel CPU、iGPU 和 NPU 用户什么时候真正拿到新模型能力。


### 对程序员的影响

做本地 AI、隐私敏感应用或边缘部署的团队，多了一批可直接进入 OpenVINO 工具链的新架构。落地时仍要锁定依赖版本，并在目标硬件上实测首 Token 延迟、吞吐、峰值内存和量化后的精度；“支持导出”不是生产性能承诺。

版本兼容表本身也是选型信息。如果团队不能长期维护转换适配，优先选择已进入主流推理后端的模型，通常比追最新参数更省工程成本。


### 江小北观点角度

模型只是本地 AI 护城河的一部分，编译器和运行时同样关键。真正影响开发者体验的，往往是一个新架构要等多久才能被稳定导出、量化并跑在现有硬件上。

技术选型最好同时维护“模型榜单”和“部署兼容矩阵”。模型能力领先两周，如果推理后端要补三个月，业务上未必更先进。

# 今日最值得写的一条

## 首选：Agent Plugins 1.0.0

这条比“又一个插件规范”更值得写。它把近期最热的 Skills 和 MCP 放进同一个软件交付问题里，也留下了足够明确的技术矛盾：可移植性先到了，安装、权限、签名、沙箱和来源信任还没到。

### 建议标题

- 《Agent 的“npm 时刻”来了，但真正的坑才刚开始》
- 《Skills + MCP 之后，Agent 生态缺的不是能力，而是一个能搬家的包》
- 《OpenAI、Google、微软都在推进 Agent 插件标准，程序员先别急着装》

### 核心论点

MCP 是调用协议，Skills 是经验说明书，Agent Plugins 才开始定义交付包。统一包装会让 Agent 能力复用更快，也会让恶意命令、过期依赖和越权工具传播更快。因此，插件生态的下一场竞争将落到软件供应链能力上。

### 建议文章结构

1. 为什么有了 Skills 和 MCP，还缺一个 Agent Plugin。
2. 1.0.0 到底标准化了什么，哪些能力仍要客户端适配。
3. 为什么“能安装”不能等同于“可信任”。
4. 注册中心、签名、SBOM、权限与沙箱将如何成为下一层基础设施。
5. 程序员现在就能做的三件事：拆分可移植核心、锁定依赖、隔离执行权限。
